# PayPal sandbox integration

This integration is sandbox-only. Connect with sandbox REST app credentials; they are held in the server process for 30 minutes and removed on disconnect or process restart. The HttpOnly same-site cookie contains an opaque random session identifier, not credentials. Memory is process-local: multi-instance/serverless deployments can lose sessions or proposals and must not be treated as a production-ready credential or approval store. Use HTTPS outside localhost and avoid request-body logging. No actual credentials were used during development.

Transaction Search uses 12 months of windows up to 31 days and every page; data may lag and depend on permissions. Some event codes and item/buyer identifiers are unavailable or ambiguous; unknowns are excluded from sale classification. Invoices are retrieved through the PayPal AI SDK toolkit, and plans via REST; counts are coverage indicators, not revenue. No general subscription enumeration is assumed. Monthly SALES and ORDERS insights are unavailable: the installed PayPal toolkit explicitly rejects merchant insights in sandbox. Do not enable live mode to circumvent this limitation. Empty, partial, or failed requests are not success evidence.

Actions on a connected account use that same short-lived session; demo actions use the separate server-configured sandbox credentials (`PAYPAL_SANDBOX_CLIENT_ID` and `PAYPAL_SANDBOX_CLIENT_SECRET`). Proposals also require `PAYPAL_ACTION_SIGNING_SECRET`, at least 32 bytes, held on the server. A proposal contains the complete parameters and each step; execution requires explicit approval of that exact proposal within five minutes. The server signs an HttpOnly cookie binding the proposal, account selection, session and inputs, and consumes the process-local claim before execution. Each PayPal request carries a deterministic request identifier; PayPal endpoint support varies, so it does not establish exactly-once notification delivery. This protects against ordinary replay within one process; it is not a distributed idempotency system and is unsuitable for multi-instance production. Ambiguous failures require inspecting PayPal before retrying. Compound actions may partially complete and report the first created ID. No refund, dispute, or cancellation action is available.

No sandbox account was changed in development. Tests use mock responses only. Before a real sandbox trial, review permissions, connect the correct sandbox account and explicitly approve each displayed action. Never put production credentials in these fields.

Sources: https://github.com/paypal/agent-toolkit and https://developer.paypal.com/api/transaction-search/v1/.

The optional sandbox seed script creates five catalog products and creates and requests sending three USD 180 invoices dated 2026-10-01. It does not create or capture orders; buyer approval is a separate step. Run only after explicit authorization and target-account review, using `node --import tsx scripts/seed-sandbox.ts --confirm-create-sandbox-demo --receipt /absolute/path/to/receipt.json` with sandbox credentials and sandbox buyer email in environment variables. The local receipt binds a run to the account and buyer, journals each step before execution and stops after an unknown outcome; inspect PayPal and reconcile the receipt before any retry. Past invoice-date acceptance is not verified in a live sandbox; successful send responses still require PayPal status and amount readback. Set `PAYPAL_SANDBOX_DEMO_INVOICE_IDS` to the three verified invoice IDs in receipt order before using the synthetic demo invoice reminders. Tests are mocked; this seed has not been executed against an account.

The installed `@paypal/agent-toolkit/ai-sdk` is used for invoice listing and invoice creation, and is tried first for 31-day paginated transaction search. It runs only fixed, allowlisted calls, never model-directed dispatch. If the read-only transaction tool fails, REST is the explicitly reported fallback; the write path never retries an uncertain SDK result through REST. SDK calls are disabled when `DEBUG` is set because its debug traces can include payloads. The installed SDK's send/reminder wrappers send `invoice_id` in the JSON body and do not expose the `send_to_invoicer` control; the direct sandbox REST calls retain the intended notification settings. Its product/plan wrappers log raw API error bodies or Axios errors, so these two approved steps use the sandbox REST client to avoid logging sensitive data. Each write still uses a step-specific PayPal request ID, without claiming exactly-once behavior for endpoints where PayPal does not guarantee it. The SDK's sandbox insights tool explicitly returns unsupported. Source: https://github.com/paypal/agent-toolkit/tree/main/typescript/src and https://developer.paypal.com/api/invoicing/v2/invoices-send/.

Subscription coverage is a bounded observation, never an account-wide total. Only Transaction Search `transaction_info` entries whose `paypal_reference_id_type` is `SUB` and whose reference has the `I-` subscription-ID format are used; other reference types and inferred billing agreements are ignored. At most 50 distinct IDs are queried, using sandbox GET subscription details. The response exposes only aggregate status counts and explicitly supplied consecutive failed-payment counts, with retrieved, failed and not-queried denominators. Missing IDs, Transaction Search failure, missing response fields, and permissions leave corresponding facts unknown. Consecutive failures reset after a successful payment, so they are not a history of all failed payments. IDs, subscriber names, emails and response bodies are not returned or logged. The installed Agent Toolkit's subscription-details tool writes raw API error objects to console; sandbox REST is used to preserve the no-payload-logging boundary. Sources: [Transaction Search reference ID types](https://developer.paypal.com/api/transaction-search/v1/definitions/transaction_detail_list/) and [subscription fields](https://developer.paypal.com/api/subscriptions/v1/definitions/subscription/).
