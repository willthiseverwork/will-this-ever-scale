# Live PayPal transaction foundation — disabled

This is an unconnected server-side foundation, not a live integration, a merchant connection flow, an automatic daily sync, or a reconciled financial ledger. No route, scheduler, durable storage, token acquisition, secrets, or account has been configured. The existing sandbox remains separate. `createLiveTransactionReader` defaults to no network unless its caller explicitly supplies `enabled`, a token, a verified merchant binding, and confirmation of the transaction-read grant. Those booleans are assertions by trusted server code, not proof; do not wire them to user input or environment flags without implementing and independently verifying the actual authorization and merchant-binding flow. Only the fixed PayPal production host and GET Transaction Search are available. No browser or caller-supplied URL is accepted. No credential or response payload is logged.

## Access findings and owner decision

PayPal's [Transaction Search reference](https://developer.paypal.com/api/transaction-search/v1/search-get/) specifies client-credentials OAuth and `https://uri.paypal.com/services/reporting/search/read`; that establishes an account's API scope, not an established third-party merchant delegation mechanism for this product. [Log in with PayPal](https://developer.paypal.com/log-in/how-it-works/) is an identity flow sharing basic non-financial account information and does not establish permission to fetch transaction history. It is available to merchants and customers in all countries according to that identity page; this does not establish financial API availability in every country. PayPal's [multiparty invoicing guide](https://developer.paypal.com/platforms/invoicing/integrate) is for select partners and specifies `INVOICE_READ_WRITE` plus `ACCESS_MERCHANT_INFORMATION`, so it does not prove a read-only invoice grant. No invoice adapter is activated.

Before a commercial connection can be enabled, the account owner must obtain PayPal's written confirmation of an approved third-party merchant-consent and revocation path for Transaction Search, permitted regions, merchant binding and the exact least-privilege scopes; separately confirm whether invoice *read-only* delegation is available. If not, decide whether another compliant acquisition method fits the product. Do not ask sellers to enter API secrets or represent identity login as financial consent. No partner application, account creation or scope grant has been initiated.

## Sync contract and limits

PayPal says Transaction Search covers the prior three years, has up to a three-hour execution-to-report delay, and limits each date range to 31 days. The collector reads every page in windows of at most 31 days. It commits a window to its result only after all pages succeed; a failure reports partial coverage and the last completed boundary. `fetchedAt` is an observation time, not a guarantee of freshness. No last-success watermark should advance on partial results. Choose an overlap/backfill policy and account for reporting lag once real behavior is confirmed; a daily run alone does not guarantee complete data, especially later status changes. No schedule exists.

PayPal explicitly says a transaction ID may appear more than once, including balance-affecting and non-balance-affecting entries. The exact-observation hash is only a deterministic fingerprint; it is not a transaction identity, cannot resolve updates, distinct identical records, boundary overlap or produce financial totals. Windows are replaceable snapshots and every result carries `reconciliation: requires_review`. Before use in comparisons, design and validate a durable merchant-isolated, encrypted store, pagination consistency, overlapping-window reconciliation, deletion/revocation, concurrency/idempotency, and a provider-supported identity/duplicate policy against actual authorized data. Treat invoices and unverified periods as unknown, never zero. No real-account results have been tested.

## Verification handoff

Mock tests cover fail-closed access, host and redirect restrictions, invalid ranges, multi-page failure and fingerprint behavior. They were authored for the hosted verification pipeline and not run locally under this task's production-only constraint. Production verification remains pending: hosted tests/build, actual authorized read-only grant and account binding, representative multi-page backfill and overlap, status changes, error recovery, revocation, privacy/secret controls, and daily scheduled run/readback. No deployment is authorized by this document.

The optional `runDailySnapshot` abstraction bounds a requested interval and performs at most one read pass. It never calls its commit interface for a partial result; a complete snapshot can be atomically committed by a future merchant-isolated store with compare-and-swap and a stable idempotency key. The abstraction itself does not provide that store, a scheduler, overlap reconciliation, or evidence of freshness. A commit exception is an uncertain outcome: the store must reconcile the operation ID before any retry. No real daily sync has been enabled.
