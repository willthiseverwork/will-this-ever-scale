# WTES read-only MCP — source prepared, not connected

The source defines a stateless Streamable HTTP MCP endpoint at `/mcp` for protocol 2025-11-25. The anonymous `demo_summary` returns a fixed synthetic shop; it is not live PayPal or a real customer. Authenticated read-only tools expose the latest saved workspace summary, product rankings with opaque IDs by default; labels are included only when the workspace setting explicitly allows sharing, monthly comparisons, reminders and general issue questions. They do not modify data or send messages. Snapshot source, period, capture time and limits accompany financial results. Buyer names, email addresses and raw rows are not exposed. A saved snapshot is not an automatic PayPal refresh.

The endpoint is not deployed, tested in a hosted client, installed, or connected. `plugins/wtes/` is source for a private portable OpenAI plugin, pointing at the intended production path; the existing production host is documented in README but the new endpoint is unverified. Do not upload or claim an active plugin until it is deployed and discovered. Claude custom connectors use the same hosted `/mcp` URL through Claude's own connector UI; this package is not a Claude installation or claim of compatibility. No public directory submission is prepared.

## Account authorization gate

Account tools do not accept browser cookies, user IDs in parameters, unsigned JWTs or client-provided key URLs. They use WorkOS RSA signatures and a verified token subject as the sole workspace key. Account access fails closed until `WTES_MCP_WORKOS_ISSUER` (exact HTTPS issuer origin), `WTES_MCP_RESOURCE_URL` (exact `https://app.willthiseverscale.com/mcp`) and `WTES_MCP_READ_SCOPE` are configured, and WorkOS actually issues tokens with matching `iss`, `aud`, `exp`, `sub` and scope. The issuer must publish `/oauth2/jwks`. Verify the exact WorkOS issuer, metadata, OAuth authorization-code with PKCE, client registration/CIMD support, resource audience and scope issuance with WorkOS before configuration; the existing website login session does not establish this. Resource metadata is 503 until configured. Authentication failure is 401 and key service failure 503. A token's `user_...` subject must be the same WorkOS user ID used by the workspace. No identity exchange or linkage is guessed.

## Protocol and support handoff

The canonical path-aware resource metadata is `/.well-known/oauth-protected-resource/mcp`; the root path is also served. The challenge identifies the path-aware URL. Browser origins are allowlisted and receive explicit preflight and CORS headers; other origins are rejected. The endpoint returns JSON, negotiates supported handshake versions 2025-11-25, 2025-06-18 and 2025-03-26, rejects unsupported version headers, and responds 405 to optional GET streaming. It has no SSE stream. Client compatibility is not verified until exercised in each host. OpenAI's tool-level authentication metadata and HTTP 401 challenge are included, but actual linking UI and host handling of the combined response remain unverified.

[WorkOS Connect metadata](https://workos.com/docs/reference/workos-connect/metadata) documents `https://<authkit-domain>/.well-known/oauth-authorization-server` and `<authkit-domain>/oauth2/jwks`; do not substitute the WTES site's own issuer. Its [MCP guide](https://workos.com/docs/authkit/mcp) says a registered Resource Indicator causes `aud` to match the requested resource; without one the requested resource is ignored and audience defaults to the environment client ID. Register the exact resource in WorkOS only after confirming intended tenant, and verify Connect/CIMD or DCR, scope issuance, consent and matching subject. The existing website cookie flow does not configure these capabilities.
