# WTES read-only MCP — public demo live, account connection pending

The source defines a stateless Streamable HTTP MCP endpoint at `/mcp` for protocol 2025-11-25. The anonymous `demo_summary` returns a fixed synthetic shop; it is not live PayPal or a real customer. Authenticated read-only tools expose the latest saved workspace summary, product rankings with opaque IDs by default; labels are included only when individually reviewed and the workspace setting explicitly allows sharing, monthly comparisons and general issue questions. They do not modify data or send messages. Snapshot source, period, capture time and limits accompany financial results. Buyer names, email addresses and raw rows are not exposed. A saved snapshot is not an automatic PayPal refresh. Private tools additionally require the workspace owner to enable assistant workspace sharing; this defaults off for new and existing workspaces and is checked on each request. Turning it off blocks the next request even for a previously issued token, but cannot retract data already shared. Product labels additionally require their separate opt-in and individual review. Reminders and test records are not exposed by these tools. The assigned read scope is `summaries:read`.

The endpoint is deployed on the production app alias. Production initialize, tools/list and the synthetic `demo_summary` call returned 200; the configured protected endpoint rejects anonymous private access with 401, and protected resource metadata returns 200. `plugins/wtes/` supplies a portable OpenAI plugin package. Local Codex and Claude Code 2.1.309 clients are configured; owner authorization, a real private account connection and client lifecycle remain unverified. Claude custom connectors use the same hosted `/mcp` URL through Claude's own connector UI; this package is not a Claude installation or claim of compatibility. No public directory submission is prepared.

## Account authorization gate

Account tools do not accept browser cookies, user IDs in parameters, unsigned JWTs or client-provided key URLs. They use WorkOS RSA signatures and a verified token subject as the sole workspace key. Production has the WorkOS issuer, exact `https://app.willthiseverscale.com/mcp` resource and `summaries:read` scope configured. Account access requires WorkOS tokens with matching `iss`, `aud`, `exp`, `sub` and scope. The issuer must publish `/oauth2/jwks`. The two public PKCE clients are registered and assigned the scope; owner login, token issuance, audience and subject matching still need live verification. The existing website login session does not establish this. Resource metadata is 503 until configured. Authentication failure is 401 and key service failure 503. A token's `user_...` subject must be the same WorkOS user ID used by the workspace. No identity exchange or linkage is guessed.

## Protocol and support handoff

The canonical path-aware resource metadata is `/.well-known/oauth-protected-resource/mcp`; the root path is also served. The challenge identifies the path-aware URL. Browser origins are allowlisted and receive explicit preflight and CORS headers; other origins are rejected. The endpoint returns JSON, negotiates supported handshake versions 2025-11-25, 2025-06-18 and 2025-03-26, rejects unsupported version headers, and responds 405 to optional GET streaming. It has no SSE stream. Client compatibility is not verified until exercised in each host. OpenAI's tool-level authentication metadata and HTTP 401 challenge are included, but actual linking UI and host handling of the combined response remain unverified.

[WorkOS Connect metadata](https://workos.com/docs/reference/workos-connect/metadata) documents `https://<authkit-domain>/.well-known/oauth-authorization-server` and `<authkit-domain>/oauth2/jwks`; do not substitute the WTES site's own issuer. Its [MCP guide](https://workos.com/docs/authkit/mcp) says a registered Resource Indicator causes `aud` to match the requested resource; without one the requested resource is ignored and audience defaults to the environment client ID. The exact resource is configured; verify scope issuance, consent, audience and matching subject with the registered clients. The existing website cookie flow does not configure these capabilities.

The registered public PKCE clients use `summaries:read`; callbacks are saved as `http://127.0.0.1:43123/callback/oRjx-MeDTBGQ` for Codex and `http://localhost:8080/callback` for Claude Code. Callback acceptance and issued tokens have not been verified. The local clients are configured; the account owner can initiate each login with:

```sh
codex mcp login wtes-private --scopes summaries:read
claude mcp login wtes-private
```

Codex discovers the exact resource automatically; an explicit resource override was removed because it duplicated the authorization request parameter. Claude Code automatically requests `offline_access` for renewable sessions. This adds no data scope; the `summaries:read` grant and workspace sharing check still apply to every private request. Renewal is within the approved connection, while initial owner authentication remains required.
